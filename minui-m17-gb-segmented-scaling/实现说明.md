# GB 分段整数倍缩放落地说明（按你的 8/8 方案）

MinUI M17 · GB/GBC 160×144 → 320×272 · 基于 HEAD `dbf8943`（2025-11-27）

本轮**按你定的方案实施**：上下各 8 源行 1×、中间 128 源行 2×。上一轮对比指出的 E / F / B' 变体一律不采用；顶部第一框会被压扁是这个方案本身的已知取舍，见 `MinUI-缩放方案对比/BGB-对比结论.md`。

## 一、行分配

| 段 | 源矩形 | 目标矩形 | 纵向倍数 | 横向倍数 |
|---|---|---|---|---|
| 上 | `{0,0,160,8}` | `{80,0,320,8}` | 1× | 2× |
| 中 | `{0,8,160,128}` | `{80,8,320,256}` | 2× | 2× |
| 下 | `{0,136,160,8}` | `{80,264,320,8}` | 1× | 2× |

- 源行 `8+128+8 = 144`，目标行 `8+256+8 = 272`，横向 `160×2 = 320`。
- `(480-320)/2 = 80`，左右各 80 px 黑边由屏幕提供，三段都不写。
- 三段各自都是整数倍 → 最近邻下零插值、零模糊。

## 二、改动范围：只 1 个文件、35 行

`workspace/m17/platform/platform.c`：

1. **文件头部（原第 21 行 `///////////////////////////////` 之后）**：5 个宏
   ```c
   #define GB_SEGMENTED_SCALE  1   // 改 0 即完全恢复原版
   #define GB_SEG_TOP          8
   #define GB_SEG_MID        128
   #define GB_SEG_BOT          8
   #define GB_SEG_W          320
   ```
   想调整压缩带分配（例如 0/16），只改这三个数即可，前提仍是 `TOP+MID+BOT=144`、`TOP+MID*2+BOT=272`。

2. **`PLAT_flip()` 内，原 `dst_rect = NULL;` 之后、`if (aspect==0)` 之前**：新增分支用三次 `SDL_RenderCopy` 画三段，随后 `SDL_RenderPresent` + `vid.blit=NULL` + `return`。

**原有的 Native / Aspect / Fullscreen / Cropped 分支一行未改**，其他平台（其他 `platform.c`）完全不受影响。

触发条件（四项同时满足，避免误伤）：
```c
vid.sharpness != SHARPNESS_CRISP &&
vid.blit->src_w == 160 && vid.blit->src_h == 144 &&
1.1721 < vid.blit->aspect < 1.1722        // 320/273 = 1.1721612
```
`320/273` 正是上一轮已实机验证的 4 字节 patched 核心报告的比例；原版 `10/9`、`4/3` 等核心不会触发。`Crisp` 会先按 `hard_scale=4` 预放大纹理，源坐标需要 ×4，因此**故意不分段**，自动走原路径 —— 所以请用 `Sharp`（最近邻）。

## 三、为什么还需要一个 elf，以及为什么可以放进 pak

`PLAT_flip()` 编译进 `minarch.elf`（见 `workspace/all/minarch/makefile` 的 `SOURCE` 含 `platform.c`），pak 只能换 `.so` / `launch.sh` / `default.cfg`，换不了平台后端 —— 所以这一步必须编译。

但 `minarch.elf` **不依赖自身路径**（已核对，只用 `/proc/self/stat` 读进程状态），且 `minui.c` 是通过 `queueNext("'<pak>/launch.sh'")` 启动 pak 的。因此把这个 elf **直接放进 `GB.pak/`**、让 `launch.sh` 优先调用它即可：

- 只有 `GB.pak` 用它；其他 pak / 核心仍走系统 PATH 的 `minarch.elf`。
- `.system/` 一个字节都不动，符合「不改原 MinUI 结构」。
- `launch.sh` 逻辑：`[ -f "$CORES_PATH/minarch.elf" ]` → `chmod +x` 后使用；否则退回 `minarch.elf`（系统版）。**没有 elf 时 pak 不会坏，仍是上一轮已验证的 A 方案画面**。

## 四、编译步骤（本机已实际跑通）

**本轮已在本机 Docker 里编译成功**：产物 `GB.pak/minarch.elf`（72,816 字节，sha256 `1bd2bd8b…f10`）已随包附带。走的是下面的轻量链路 B，不需要等数小时的 buildroot。

### B（已跑通）：Debian buster armhf 交叉工具链

```sh
# 1) 构建镜像（实测 1 分 22 秒）
cd MinUI-GB分段缩放/tools/quick-build
docker build -t m17-quick --progress=plain .

# 2) 编译（源码目录 = 已打补丁的 MinUI-src/workspace）
cp build-inside.sh <MinUI源码>/workspace/build-inside.sh
MSYS2_ARG_CONV_EXCL='*' docker run --rm \
  -v "/path/to/MinUI/workspace:/root/workspace" \
  m17-quick sh /root/workspace/build-inside.sh
# 产物：workspace/minarch-segmented.elf
```

`build-inside.sh` 的三个关键点：
- 先交叉编译 `libmsettings.so`、拷贝 `msettings.h` 到 `/usr/arm-linux-gnueabihf/`，否则 minarch 链接不到 `-lmsettings`；
- `ARCH="-O3 -mfpu=neon -fno-pie"`：Debian 交叉 gcc 默认 `vfpv3-d16`，LTO 阶段会生成 `vldmia {q8-q15}` 而汇编报错，必须显式给 NEON；
- `LIBS="-flto -mfpu=neon -no-pie"`：Debian gcc 8 默认输出 PIE，官方 `minarch.elf` 是 `EXEC`，用 `-no-pie` 对齐。

另补了两个编译前置文件：`workspace/hash.txt`（`BUILD_HASH`）与 `workspace/all/minarch/libretro-common/include/libretro.h`（只需这一个头，避免 clone 整个 libretro-common 仓库）。

### A（官方同源，备用）：union-m17-toolchain

```sh
cd /path/to/MinUI
git apply /path/to/gb-segmented-8-128-8.patch
make shell PLATFORM=m17          # 自动构建 buildroot 2018.02-rc3 镜像
sh /root/workspace/tools/build-minarch.sh /root/workspace/minarch-segmented.elf
cp /root/workspace/minarch-segmented.elf /sdcard/Emus/m17/GB.pak/minarch.elf
```
本轮也启动了这条链路（`docker build -t m17-toolchain`，日志 `tools/docker-build.log`），但完整 buildroot 需编译 gcc 6.4 + glibc 2.26 + SDL2 全家桶 + rootfs，耗时以数十分钟计。仓库内无预编译 `m17-toolchain.tar.xz`、无 release 资产，无法跳过。

**B 为何可替代 A**：产物与官方 `v20251127-1` 的 `.system/m17/bin/minarch.elf` 逐项对照 —— 9 个 `DT_NEEDED`、`PT_INTERP`、hard-float ABI、`EXEC` 类型、glibc 符号需求（`GLIBC_2.4/2.7`）完全一致，未定义符号没有新增；反汇编证实多了 3 次 `SDL_RenderCopy` + 1 次 `SDL_RenderPresent`。详见 `ELF核对.txt`（20/20 PASS）与 `本机构建说明.md`。

## 五、实机使用与验证

1. 整个 `GB.pak/` 放到 `/sdcard/Emus/m17/GB.pak/`（文件夹名不能改，`EMU_TAG` 决定存档路径）。
2. 进 GB 游戏 → Menu → Options → `Screen Scaling = Aspect`、`Screen Sharpness = Sharp`。
   ⚠️ `.userdata` 下的 user cfg 优先级高于 pak 的 `default.cfg`，若之前手动改过，要在菜单里重新选一次。
3. 预期画面：`x=80..399`；中间 `y=8..263` 是均匀 2×2；上下各 8 行是 2×1 扁像素。顶部第一个选项框会明显被压扁（BGB 截图里那 8 行有 37.2% 内容）—— 这是你选定方案的固有取舍。
4. 定量：`adb` 抓 `/dev/fb0`（480×272 RGB565），非黑区应为 `x=80..399, y=0..271`。
5. 对照：把 pak 里的 `minarch.elf` 临时移走 → 立刻回到 A 方案（16 个细行散布全屏），可直接对比。
