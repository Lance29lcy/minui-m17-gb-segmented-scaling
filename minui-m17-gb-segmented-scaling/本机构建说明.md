## 一、上一轮为什么没编出来

- Docker Desktop 引擎当时启动 7 分 34 秒无响应，`docker info` 连不上 `dockerDesktopLinuxEngine`；`wsl.exe` 在安全策略黑名单。
- 本机只有 **bare-metal** `arm-none-eabi-gcc`，没有 Linux glibc sysroot、SDL2 ARM 库、`libmsettings.so`，只能做语法/目标码验证，链接不出 Linux ELF。
- 官方工具链仓库无预编译 `m17-toolchain.tar.xz`，也无 release 资产，跳过 buildroot 的捷径不存在。

## 二、本轮的四个突破

1. **Docker Desktop 引擎已恢复**：`docker version` 正常返回 Server 29.8.0 / Docker Desktop 4.91.0，`docker pull debian/eol:buster-slim` 成功。
2. **网络**：GitHub API 被限流，但 `raw.githubusercontent.com` 走本机代理 `127.0.0.1:6973` 可达；Docker 容器内网络直连可用。本机 git 全局代理端口写错成 `7897`，用
   `git -c http.proxy=http://127.0.0.1:6973 -c https.proxy=... clone` 成功克隆 `union-m17-toolchain`。
3. **CRLF**：Windows 上 clone 下来的 `Dockerfile` / `support/*.sh` / buildroot `.config` 全是 CRLF，在 Linux 容器里 `#!/bin/sh\r` 会直接失败。已用脚本统一转 LF。
4. **基础镜像的 apt 源**：`debian/eol:buster-slim` 自带指向 `archive.debian.org` 的源，`apt-get update` 实测可用；`dpkg --add-architecture armhf` 也能拉到 armhf 包。

## 三、两条链路

### A. 官方同源（buildroot 2018.02-rc3）

`make shell PLATFORM=m17` → 构建 `m17-toolchain` 镜像（gcc 6.4 / glibc 2.26 / SDL2 全家桶 / rootfs），耗时数十分钟。本轮已启动该构建（日志 `tools/docker-build.log`），运行约 12 分钟仍停在 `host-gcc-initial-6.4.0`，已主动停止后台构建：链路 B 已产出 ABI 与官方逐项一致的可执行文件，A 非必需。若日后需要完全同源版本，重跑 `docker build -t m17-toolchain .` 即可（Docker 层缓存可复用），再用 `tools/build-minarch.sh` 编译。

### B. 轻量链路（本轮成功，约 1.5 分钟建镜像 + 数秒编译）

`tools/quick-build/Dockerfile`：基于 `debian/eol:buster-slim`，装
`gcc-arm-linux-gnueabihf`、`libc6-dev-armhf-cross`、`libsdl2-dev:armhf`、
`libsdl2-image-dev:armhf`、`libsdl2-ttf-dev:armhf`、`zlib1g-dev:armhf`。

```sh
# 1) 构建镜像
cd MinUI-GB分段缩放/tools/quick-build
docker build -t m17-quick --progress=plain .

# 2) 编译（把脚本放进挂载目录，避免中文路径传给 docker）
cp build-inside.sh <MinUI源码>/workspace/build-inside.sh
MSYS2_ARG_CONV_EXCL='*' docker run --rm \
  -v "/path/to/MinUI/workspace:/root/workspace" \
  m17-quick sh /root/workspace/build-inside.sh
# 产物：workspace/minarch-segmented.elf
```

`MSYS2_ARG_CONV_EXCL='*'` 是 Git Bash 必需：否则 `-v` / `-w` 里的 `/root/...` 会被 MSYS 转成 Windows 路径，Docker 报 "working directory … is invalid"。

## 四、编译前补齐的文件与三个坑

| 问题 | 处理 |
|---|---|
| `BUILD_HASH!=cat ../../hash.txt` 找不到文件 | 新建 `workspace/hash.txt`，内容 `dbf8943` |
| `make` 的 `libretro-common:` 目标会 clone 整个仓库 | 只下载一个头文件到 `workspace/all/minarch/libretro-common/include/libretro.h`（源码只用 `#include "libretro.h"`） |
| `-lmsettings` 找不到 | `build-inside.sh` 先用交叉 gcc 编 `msettings.c` 成 `libmsettings.so`，并把 `msettings.h` 放进 `/usr/arm-linux-gnueabihf/include/` |
| **LTO 汇编报错** `VFP single precision register expected -- vldmia r1!,{q8-q15}` | Debian 交叉 gcc 默认 `vfpv3-d16`，而 LTO 生成 NEON q8-q15；`ARCH` 加 `-mfpu=neon` 后解决 |
| 生成的是 **PIE (DYN)**，官方是 **EXEC** | `ARCH` 加 `-fno-pie`、`LIBS` 加 `-no-pie`，重编后类型与官方一致 |

最终编译命令（makefile 原始 flags 全部保留，只覆盖 `ARCH` / `LIBS`）：

```sh
make PLATFORM=m17 \
  ARCH="-O3 -mfpu=neon -fno-pie" \
  LIBS="-flto -mfpu=neon -no-pie"
```

## 五、与官方 ELF 的逐项对照（20/20 PASS）

| 检查项 | 官方 v20251127-1 | 本机产物 | 结论 |
|---|---|---|---|
| Class / Data / Machine | ELF32 / LE / ARM | 同 | 一致 |
| Flags | `0x5000400` hard-float ABI | 同 | 一致 |
| Type | `EXEC` | `EXEC` | 一致 |
| PT_INTERP | `/lib/ld-linux-armhf.so.3` | 同 | 一致 |
| DT_NEEDED | 9 个，含 `libmsettings.so`、`libSDL2-2.0.so.0` 等 | 完全相同 | 一致 |
| glibc 符号版本 | `GLIBC_2.4`, `GLIBC_2.7` | 同 | **无 2.28 新符号**，设备 glibc 2.26 可加载 |
| 未定义符号 | 138 | 137（仅少 `_Jv_RegisterClasses`） | **无新增符号**，不会 undefined symbol |
| ARM 属性 | — | `7-A` / `NEONv1` / VFP registers | Cortex-A7 匹配 |
| `SDL_RenderCopy` 调用点 | 3 | 6 | **多 3**：分段循环被展开 |
| `SDL_RenderPresent` 调用点 | 3 | 4 | **多 1**：分段分支提前 return |
| 分段常数 | — | 8/128/160/256/272/320 全在机器码中 | 补丁确实编进去了 |
| `BUILD_HASH` | — | `dbf8943` | 源码版本正确 |

`PLAT_flip.constprop.21` 反汇编里可见连续三次 `blx … <SDL_RenderCopy@plt>` 紧跟一次 `SDL_RenderPresent@plt`，正是三段绘制 + 提前返回。

## 七、复现核对

```sh
cd MinUI-GB分段缩放
python tools/verify_elf.py \
  --elf GB.pak/minarch.elf \
  --reference tools/reference/minarch.elf \
  --pak GB.pak --out ELF核对.txt
```
需要 `arm-none-eabi-readelf` / `arm-none-eabi-objdump` 在 PATH（本机 Arm GNU Toolchain）。
